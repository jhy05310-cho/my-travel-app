# 출처 검증 리서치

## 이 스킬이 막으려는 실패

리서치 결과물의 실패는 대부분 "틀린 정보"가 아니라 **"확인 안 한 걸 확인한 것처럼 쓴 것"** 이다. 아래 4가지가 반복된다.

| 실패 유형 | 증상 | 이 스킬의 대응 |
|---|---|---|
| 기억 기반 서술 | 학습 데이터의 낡은 사실을 현재형으로 씀 | §1 fetch 강제 |
| 검색 스니펫을 출처로 사용 | 검색엔진 요약을 원문 인용처럼 씀 | §2 스니펫 ≠ fetch |
| 순환 재인용 | 여러 블로그가 같은 문장을 복제한 것을 "다수 출처"로 셈 | §3 출처 등급 |
| 자기 검증 | 쓴 사람이 스스로 채점 | §5 작성자/검증자 분리 |

---

## 1. fetch하지 않은 것은 쓰지 않는다

- 모든 사실 문장에 **실제 fetch에 성공한 URL**을 붙인다.
- fetch 실패 / 원문 미확인은 `[미확인]` 으로 표기한다. **추측으로 메우지 않는다.**
- 차단·404·인증 필요로 못 읽은 URL은 "시도했으나 실패" 목록에 그대로 남긴다. 숨기면 독자가 커버리지를 오판한다.
- 조사 범위를 다 못 채웠으면 **"전량 조사했다"고 쓰지 않는다.** 실제 커버리지 구간을 명시한다.

## 2. 검색 스니펫은 출처가 아니다

WebSearch 결과의 요약문은 검색엔진이 생성한 것이다. 원문이 아니다.
- 스니펫으로 알게 된 사실은 **반드시 해당 URL을 WebFetch로 열어 확인**한다.
- 열지 못했으면 그 사실은 `[미확인]` 이다. 스니펫을 인용 근거로 쓰지 않는다.

## 3. 출처 등급을 매긴다

| 등급 | 정의 | 예 |
|---|---|---|
| **1차** | 주체 본인이 발행한 문서 | 공식 docs, 벤더 공식 블로그, 논문 원문(abs/PDF), 표준 스펙 |
| **2차** | 1차를 인용·해설한 것 | 공식 GitHub 저장소 README, 기술 미디어 |
| **3차** | 2차를 재인용한 것 | 개인 블로그, awesome-list, SEO 요약글 |

규칙:
- 등급이 낮은 출처는 **"X가 그렇게 정리했다"** 까지만 참이다. 사실 자체의 근거로 승격하지 않는다.
- **여러 3차 출처가 같은 문장을 반복하는 것은 교차검증이 아니다.** 콘텐츠 팜 복제일 수 있다. 원문 1개를 찾는 게 3차 출처 10개보다 낫다.

## 4. 정량 수치는 sanity check를 통과해야 인용한다

숫자를 API/문서에서 읽었다고 끝이 아니다. **그 숫자가 현실에서 말이 되는지** 따진다.
- 순위·규모 수치는 알려진 상한과 비교한다. (예: GitHub star는 최상위 저장소가 40만 수준)
- 말이 안 되는 수치는 "API가 이렇게 응답했다"까지만 쓰고, **현실 반영 여부는 별도로 검증하거나 `[미검증]` 표기**한다.
- 데이터 소스가 실제 서비스가 아니라 미러/샌드박스일 가능성을 확인한다. (알려진 저장소의 owner명이 실제와 다르면 미러다)

## 5. 작성자와 검증자를 분리한다

<!-- 근거(공식 문서 원문): "A reviewer running in a fresh subagent context sees only the diff
     and the criteria you give it, not the reasoning that produced the change, so it evaluates
     the result on its own terms." https://code.claude.com/docs/en/best-practices -->

1. 조사 에이전트는 각자 **독립 컨텍스트**에서 조사하고 **요약만** 반환한다. 원문을 메인 컨텍스트에 붙여넣지 않는다.
2. 각 조사 에이전트에게 **"자신 없는 주장 3개"** 를 스스로 신고하게 한다.
3. 조사가 끝나면 **별도 에이전트**에게 결과를 넘기고 *"출처 없는 단정, 과장, 최신성 오류를 찾아 반박하라"* 고만 지시한다. 칭찬·총평을 금지한다.
4. 반증 결과를 **본인이 1차 출처로 재확인**한다. 반증자도 틀릴 수 있다.
5. 확정된 오류는 문서에서 **지우지 말고 정정 표시**로 남긴다. 무엇이 왜 틀렸는지가 다음 조사의 자산이다.

## 6. 최신성 태깅

- 조사 기준일을 문서 맨 위에 쓴다.
- 조사창(기본 3개월)보다 오래된 정보는 `[stale: YYYY-MM]` 을 붙인다.
- **가까운 미래에 예정된 변경**을 별도 항목으로 뽑는다. 이미 지난 변경보다 행동에 더 중요하다.

## 7. 산출물 체크리스트

보고서를 끝내기 전에 전부 예여야 한다.

- [ ] 모든 사실 문장에 fetch 성공한 URL이 붙어 있다
- [ ] `[미확인]` 항목이 별도 섹션으로 모여 있다
- [ ] fetch 실패한 URL과 실패 사유가 남아 있다
- [ ] 출처 등급표가 있다
- [ ] 이상해 보이는 수치에 sanity check 결과가 붙어 있다
- [ ] 반증 단계를 거쳤고, 반증 결과가 문서에 반영되어 있다
- [ ] "성공했다" 대신 실행한 명령과 그 출력으로 보고했다
- [ ] 미해결 질문이 명시되어 있다

## 8. 이 스킬을 쓰지 말아야 할 때

| 상황 | 이유 | 대신 쓸 것 |
|---|---|---|
| 코드베이스 내부 탐색 | 외부 출처가 없다. 코드가 곧 1차 출처다 | Explore 서브에이전트 |
| 단발성 사실 1개 확인 | 절차 오버헤드가 이득보다 크다 | WebFetch 직접 호출 |
| 사용자가 이미 원문을 붙여넣은 경우 | 재수집 불필요 | 그대로 읽고 인용 |
| 브레인스토밍·아이디어 발산 | 검증 대상 사실이 없다 | 일반 대화 |
